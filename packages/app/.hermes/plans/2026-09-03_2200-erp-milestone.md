|---|---|---|

| **1.3** Drizzle schema: role/perm tables | `server/db/schema-perm.ts` | `npx nuxt db generate` ผ่าน, tables มี |
| **1.4** Seed 1 admin role | `server/db/seed.ts` | admin role อยู่ใน DB |
| **1.5** API: CRUD entity | `server/api/meta/entity/[...].ts` | curl POST/GET/PUT/DELETE ผ่าน |

### Phase 3: Workflow & Approval (W7–W9)

**เป้าหมาย:** สร้าง workflow กำหนดเอง → เปลี่ยนสถานะ doc → audit log ครบ

| งาน | ไฟล์ที่เกี่ยวข้อง | DoD |

| **3.6** UI: Status badge + actions | `components/meta/StatusBadge.vue` | แสดงสถานะ + ปุ่ม transition |

| **3.8** เทส์: Workflow tests | `tests/api/workflow.test.ts` | ผ่าน 10 tests |

**Phase 3 Gate:**
```bash
# 1. สร้าง workflow "pm_approval":
#    draft → submitted → approved → done (with allowed transitions)
# 2. สร้าง work_order doc → สถานะ "draft"
# 3. Submit → สถานะ "submitted"
# 4. Audit log แสดง: draft → submitted (by user, timestamp)
# 5. Approve → สถานะ "approved"
# 6. Done → สถานะ "done"
# 7. ลอง move "done" → "draft" → ต้อง fail (transition ไม่ allowed)
# 8. Permission rule: transition อนุญาตเฉพาะ role ที่มี perm "transition.<state_from>"
#    (ถ้าไม่อนุญาต → 401/403)
# 9. เทส์ผ่าน
# 10. git commit "feat(p3): workflow + audit"
```

## 3. Pattern ทำงาน (ไม่ต่างจาก cycle เดิม)

```text
ทุก Phase (P1-P4):
  1. Code ทีละ task (1.1 → 1.2 → ... → 1.10)
  2. Test ทุก task ที่สร้าง API
  3. Review: Lead ตรวจสอบ codebase + evidence
  4. Gate: DoD ทุกข้อผ่าน → git tag vX.P
  5. Evidence: เก็บใต้ D:/LOGHOLIZON/engine/evidence/pX/
  6. ถัดไป Phase ถัดไป
```

**Agent dispatch:** (ใช้ delegate_task ตาม pattern เดิม)
```text
Code Agent  → delegate_task ทีละ task (ไม่ขนานหลาย task)
              context: path ไฟล์, มาตรฐาน agent.md, บริบทจาก plan นี้
Test Agent  → delegate_task หลัง code agent เสร็จ task group
              context: วิธีรันเทส + gate จาก plan
Review Agent → delegate_task หลัง test ผ่าน
              context: review acceptance + gather evidence
Lead        → verify on disk (git log + run test + curl) → ไม่เชื่อ self-report
```

**Stack reference (อย่าเดา):** Nuxt 4[12] · NuxtHub HubDB[10] · Drizzle ORM[11] — เวลา agent สงสัย API ให้เปิด docs ก่อนเขียนโค้ด

## 4. ตรวจสอบ 5 รอบ

### Round 1: Scope แคบพอไหม?

| คำถาม | คำตอบ |
|---|---|
| Phase 1 ทำกี่วัน? | 15 วัน (3 สัปดาห์) — 10 tasks |
| Phase 1 สร้างอะไร? | CRUD entity/field + API + UI จัดการ metadata |
| ต้องสร้าง module อื่นไหมใน Phase 1? | **ไม่** — metadata engine เท่านั้น |
| Phase 2 ต้องทำ auth ไหม? | **ไม่** — auth ไม่อยู่ใน scope MVP (ตัดออก) |
| PM module ต้องสร้างหลาย entity? | **ไม่** — work_order + pm_schedule 2 ตัวพอ |
| ✅ ผ่าน | แต่ละ phase มีเป้าหมายเดียว ชัดเจน |

### Round 2: Feasibility — Nuxt 4 + HubDB + Drizzle

| คำถาม | คำตอบ |
|---|---|
| NuxtHub SQL รองรับ JSON payload? | ✅ SQLite เก็บ JSON เป็น TEXT ได้ (JSON.stringify) |
| NuxtHub DB API ถูกต้องไหม? | ✅ ใช้ Drizzle instance จาก `@nuxthub/db`; ไม่ใช้ `hubDatabase()` |
| Dynamic table (ไม่ hardcode) | ✅ metadata-driven: JSON column ใน global records table |
| รัน local ได้ไหม? | ✅ `hub.db: 'sqlite'`; NuxtHub สร้าง `.data/` local |
| Cloud deploy ใช้ไหม? | ❌ ยังไม่ใช้ใน MVP; ย้ายเป็นงานหลังผ่านทุก gate |
| ✅ ผ่าน | Nuxt + Nuxt UI + NuxtHub + SQLite local เป็น stack เดียวกัน |

### Round 3: Design — ไม่กว้างเกินไป

| คำถาม | คำตอบ |
|---|---|
| Phase 1 scope 有多大? | 10 tasks, ~15 วัน. ไม่รวม auth, ไม่รวม export |
| Dynamic form: ต้อง drag-and-drop? | **ไม่** — list-based field editor พอ (drag-and-drop = YAGNI) |
| Permission: ต้อง field-level ไหมใน MVP? | **ไม่** — role-based ระดับ entity + action (create/read/update/delete) พอ |
| Workflow: ต้อง branching logic ไหม? | **ไม่** — linear state machine: A → B → C. branching = future |
| Excel: ต้องทุก sheet? | **ไม่** — export 1 sheet, import 1 sheet. multi-sheet = future |
| ✅ ผ่าน | ทุก feature ตัดเหลือ MVP จริง |

### Round 4: Testability

| คำถาม | คำตอบ |
|---|---|
| API test ทำยังไง? | Nitro test + local SQLite ผ่าน `@nuxthub/db` |
| Form test ทำยังไง? | Component test ด้วย Vitest + @vue/test-utils |
| Workflow test ทำยังไง? | API test: transition ถูก/ผิด allowed path |
| Total tests target per phase? | Phase 1-3: 10 tests ต่อ phase. Phase 4: 10 tests |
| ✅ ผ่าน | ทุก task มีวิธีเทส์ชัดเจน |

### Round 5: Execution — ทำได้จริงไหม?

| คำถาม | คำตอบ |
|---|---|
| Solo dev + agent ทำ 12 สัปดาห์ได้ไหม? | ✅ ถ้าทำทีละ phase + ตัด scope |
| Agent pattern: Code → Test → Review ทำได้ไหม? | ✅ delegate_task ทีละ task |
| Evidence: เก็บจริงไหม? | ✅ ทุก phase gate มี git tag + evidence file |
| Rollback plan? | ✅ git branch per phase. ถ้าพัง → revert |
| เครื่องมือ local พร้อมไหม? | ⚠️ ตรวจ `.data/hub/db.sqlite` ตั้งแต่ Task 1.1 |
| ✅ ผ่าน | แผนนี้ work ได้จริงสำหรับ solo dev |

## 5. Tech Decision (ยึด)

| ตัดสินใจ | ทางเลือก | เลือก | เหตุผล |
|---|---|---|---|
| Database schema | Dynamic table per entity vs JSON column | **JSON column ใน `_data_record`** | ไม่ต้อง ALTER TABLE เมื่อเพิ่ม field |
| Auth | Implement MVP vs ตัดออก | **ตัดออก** | YAGNI. ใช้ hardcoded admin ก่อน |
| Built-in Accounting/CRM | Implement vs ตัดออก | **ตัดออก** | Decision §4[2][9] — สร้างเมื่อมีลูกค้าจริง |
| Form rendering | Drag-and-drop vs List-based | **List-based** | MVP ไม่ต้อง drag-and-drop |
| Workflow | Branching vs Linear | **Linear** | MVP ไม่ต้อง branching |
| Excel | xlsx vs csv | **xlsx (exceljs)** | ExcelJS ใช้ได้ใน Nitro |
| State management | Pinia vs composable | **composable** | เบา, ไม่ต้อง setup store || NuxtHub DB access | `hubDatabase()` vs Drizzle | **`@nuxthub/db`** | API ปัจจุบันของ NuxtHub v0.10+ |

## 11. Rollback Strategy

```text
ถ้า Phase N พัง:
  1. git log --oneline → หา commit ก่อน Phase N
  2. git revert -n HEAD~<task_count> หรือ git checkout <commit> -b rollback
  3. ตรวจสอบ: npm run dev รันได้ไหม
  4. รันเทส์ทั้งหมด
  5. ถ้าผ่าน → merge กลับ main
  6. ถ้าไม่ผ่าน → แก้ไขก่อน merge
```
